# Web JD 新消息接收修复（2026-10-24）

## 结论与范围

原有 JD WebSocket 只在发送时短连等待 ACK，Web 持续收信依赖 TIM SDK 或 HTTP 轮询。JD HTTP 读取异常且 TIM 停服时，即便独立发送成功，Web 也没有有效的新消息接收路径。

本次增加服务器持有凭据的 JD 持续接收，再经鉴权轮询、同步归档、页面合并展示。不会把归档、空列表或握手成功冒充上游历史恢复。

主要验收范围是 C2C 新文字消息。图片、语音、视频、文件使用既有 JD 归一化能力，尚未做真实端到端验收；撤回、已读等控制帧不在本次新增接收范围内。不能修复手机 APK，也不能补回断线期间上游未提供、本站未归档的历史。

## 实现

- `bbw_protocol/adapters/jd_realtime.py`：按登录运行时绑定 UID/token；单进程最多 32 个接收器，每个最多 512 条、2 MiB 缓冲，单帧 256 KiB。90 秒无人轮询释放连接；注销取消连接并清除凭据和缓冲。重连退避 1–30 秒，丢帧、换游标或断线后明确标识历史缺口。使用独立设备 ID；只发送协议心跳，不向其他用户发消息，不自动发送已读回执。
- `bbw_protocol/adapters/jd_chat.py`：登录运行时管理接收器生命周期；token 变化替换并清空旧接收器。修复 `websockets 13`/`15` 握手请求头关键字差异；原有发送 ACK、投递不确定状态和不自动重发契约保留。
- `bbw_web/jd_live.py`、`api.py`：`GET /api/im/live?cursor=...` 使用现有持久化登录校验、完整双向黑名单快照及逐对象授权，不接受用户选择 UID。独立限流 60 次/分钟，响应 `no-store`；不暴露上游 token、原始异常或任意扩展字段。
- `persistence.py`：调用既有归档事务同步提交。失败返回 503，不交出消息或新游标；重试依靠既有消息 ID 幂等。50 个对象也合并成单个有界归档批次，不超过归档的 16 个信封上限。
- `static/app.js`：前台页面约 6 秒轮询一次（5 秒下限配合 3 秒调度）；单实例在途、积压分页、错误退避。账号、会话或策略世代变化时丢弃旧响应。按既有消息身份去重，合并乐观发送回显，更新会话预览与未读；不依赖 HTTP 历史先成功，不把历史标记为加载完成。
- `static/index.html`：更新 JS 内容版本，避免继续使用旧脚本缓存。

不存在数据库迁移、依赖锁变更或镜像构建；不改生产凭据和业务配置，上线仅切换 app 的代码挂载。
