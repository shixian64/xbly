# 16 · Web 界面与数据链路性能优化

**分析日期：** 2026-07-24
**范围：** 用户端首屏、页面切换、会话列表、聊天记录、数据归档、请求可观测性
**运行基线：** 当前运行容器仍是 `bbw-app:2026.07.22-3`；本轮代码尚未部署，文中的优化后效果需要部署后复测。

## 1. 结论

界面卡顿并非单一前端问题，主要耗时来自四类叠加：

1. 静态资源请求误入带会话认证的旧路由，每个 CSS、JavaScript 请求都可能触发 Redis 和 PostgreSQL。
2. 高频接口在返回浏览器前执行重复数据库查询或逐条写入。
3. 上游响应、消息归档、产品事件和历史响应产生大量细粒度 RQ 作业与事务。
4. 长会话和列表页面存在重复 DOM 替换、过量节点、滚动任务及离屏渲染开销。

本轮已把关键路径改为：

```text
HTML/CSS/JS
  -> 直接 FileResponse，不认证、不访问数据库

业务请求
  -> 会话校验
  -> 上游请求或单次本地查询
  -> 必须同步的授权数据批量持久化
  -> 响应浏览器
  -> 非安全关键的归档与事件进入有界批处理队列
```

## 2. 优化前日志基线

旧运行版本近两小时的作业日志中，最明显的后台热点如下：

| 作业 | 次数 | 平均耗时 | 累计耗时 | 主要问题 |
|---|---:|---:|---:|---|
| `archive_message_job` | 1064 | 0.670 秒 | 713.1 秒 | 每条消息一个作业、一个事务 |
| `record_product_event` | 158 | 约 0.653 秒 | 103.1 秒 | 高频产品事件逐条入库 |
| `ingest_history_response` | 381 | 0.733 秒 | 279.2 秒 | 会话轮询重复归档相同摘要 |

`ingest_history_response` 的来源中：

- `/api/im/messages`：226 次，其中摘要请求 145 次、完整消息 81 次。
- `/api/im/conversations`：155 次。

这些作业累计占用 worker 的时间很高，还会增加 PostgreSQL 连接、事务提交、索引更新和 Redis/RQ 调度压力。当前代码已对这三类热点分别做批量化、去重或有界排队；旧容器未部署新代码，因此现有运行日志不会体现收益。

## 3. 首屏与静态资源

当前第一方首屏资源大小约为：

| 文件 | 未压缩大小 |
|---|---:|
| `index.html` | 7 KB |
| `app.css` | 126 KB |
| `app.js` | 717 KB |

Caddy 已启用 zstd/gzip，因此网络传输小于原始大小；但 JavaScript 的解析执行成本仍然存在。

已完成：

- `app.js` 放入 `<head>` 并使用 `defer`，下载与 HTML 解析并行。
- `app.css`、`app.js` 使用内容哈希查询参数，版本化资源返回一年 `immutable` 缓存。
- `/` 和 `/static/*` 改为 FastAPI 直接 `FileResponse`。
- 静态资源不再进入旧 BFF 分发，不再读取请求体、不再触碰 Session、不再执行用户绑定查询。
- 未版本化 JavaScript 保持 `no-cache`；普通图片短缓存；固定版本 vendor SDK 长缓存。
- 保留静态路径规范化和目录穿越防护。
- `/api/features` 在首屏会话恢复完成后空闲加载；登录用户直接复用 `/api/me` 已返回的功能开关。
- `/api/me` 不再同步刷新上游个人资料。
- 启动恢复增加超时、离线识别、后台重试和 `Retry-After` 支持，临时网络故障不会长期卡住启动页。

预期收益：

- 已登录用户刷新页面时，HTML、CSS、JavaScript 不再各自产生一次 Redis/PostgreSQL 认证开销。
- 二次访问可直接命中不可变资源缓存。
- 首屏不再等待功能开关和上游资料刷新。

## 4. 请求路径与数据库

### 4.1 私聊授权

私聊授权属于安全关键数据，必须在相关响应到达浏览器前持久化，不能简单改成异步任务。

已完成：

- 会话联系人授权由“每个联系人一次查询、一次 upsert”改为“一次批量读取、一次批量 upsert”。
- 内容、状态和证据均未变化的授权不再更新 `updated_at`，周期轮询通常只剩一次读取。
- 好友、黑名单快照使用同一批量写入策略；分页快照只读取本页涉及的联系人。
- 发送私信前的拉黑、关系授权、历史会话检查由最多三次数据库往返合并为一个一致性快照查询。
- `/api/im/message-policy` 原先最多五次查询、三个事务入口，现合并为一个 SQL 语句和一个数据库往返。
- 浏览器并发触发的权限刷新共用同一个 Promise，旧登录会话的迟到响应不会污染新会话。

安全语义保持不变：双向黑名单仍覆盖全局主动私信权限、好友、匹配和历史会话授权。

### 4.2 会话摘要

- `/api/im/conversations` 合并本地归档摘要时，原先先查会话、再查每个会话的最新消息。
- 现使用相关子查询和外连接一次返回会话与最新消息，减少一个数据库往返。
- 最新消息仍按 `occurred_at`、`created_at` 排序，用户隔离条件仍在查询中。

### 4.3 登录身份

- 用户状态与外部账号绑定由两次独立查询改为一次联表查询。
- 账号状态、外部账号 ID 和 provider 校验不变。

## 5. 后台任务与写入放大

### 5.1 消息归档

- 前端在 75ms 窗口内最多聚合 16 条归档请求。
- 批量 API 最大接收 20 条。
- RQ 使用一个批量作业处理一组消息。
- 数据库在一个事务中复用会话查询和 upsert，并统一派发媒体 outbox。
- 页面离开时仍受 keepalive 体积上限保护，422 时自动拆分批次。

### 5.2 产品事件

- 请求线程只把事件放入最大 1024 项的进程内有界队列。
- 每批最多 32 项，等待窗口 100ms。
- 同一用户的事件合并为一个 RQ 作业和一个数据库事务。
- `/api/im/read` 的本地已读更新也移入该批处理事务，不再阻塞接口响应。

### 5.3 历史响应

- 使用最大 64 项的有界队列，每批最多 8 项、等待 200ms。
- 按用户和外部账号分组，一个批次只加载一次账号绑定并使用一个事务。
- 会话摘要内容未变化时最多每 120 秒归档一次；内容变化仍立即归档。
- 队列满、入队失败和处理失败都有健康指标与日志，不允许无界内存增长。

### 5.4 上游原始响应

- 从同步数据库写入改为最大 64 项的有界异步队列。
- 每批最多 16 项、一个事务。
- 请求响应不再等待加密归档完成。

## 6. 前端渲染与交互流畅度

已完成：

- 聊天消息合并改为接近 O(n)，避免重复嵌套查找。
- 新消息使用增量 DOM 渲染，不再每次重建整个聊天区。
- 长会话默认只保留最近 400 条 DOM 节点，每次向上展开 200 条。
- 滚动到底部操作按帧合并，避免同一轮事件反复触发布局。
- 会话列表 HTML 未变化时跳过整表替换。
- 好友搜索每个动画帧最多更新一次，只查询当前联系人列表。
- 页面缓存限制 32 项，面板缓存 40 项，面板 DOM 缓存限制 24 项，避免长期使用后内存持续增长。
- 附近页移除重复 `/api/home` 请求。
- 长会话通过 DOM 窗口控制节点数量，列表通过缓存上限和未变化跳过替换控制布局与绘制开销；保留完整可见内容，不使用可能影响查找、辅助技术或滚动高度估算的 `content-visibility`。
- 移动端聊天头部关闭滚动期间代价较高的背景模糊。

## 7. 可观测性

服务端：

- 每个响应增加 `Server-Timing: app;dur=...`。
- `/api/` 和 `/admin` 请求超过 1000ms 时记录结构化 `slow_http_request`。
- 普通请求日志包含 request ID、路由、状态码和总耗时。
- 健康数据增加原始响应队列、产品事件队列和历史响应队列状态。

浏览器：

- 最多保存 120 条本地性能指标。
- 记录 API 客户端总耗时、HTTP 状态、服务端耗时、Long Task、LCP 和 Navigation Timing。
- 控制台只读入口：

```javascript
window.getXBLYPerformanceMetrics()
```

## 9. 验收建议

本轮不在未部署状态下承诺具体毫秒收益，部署后按同设备、同网络、同账号数据量做 A/B 对比。最低验收条件：

1. 静态资源请求不再执行 Session/用户绑定查询。
2. 相同会话列表轮询不再逐联系人写数据库。
3. 权限快照只产生一次数据库往返。
4. 会话摘要本地补全只产生一次数据库往返。
5. 三类高频后台作业从逐条作业变为批量作业，且队列无持续积压和丢弃。
6. 长会话 DOM 节点保持在窗口上限附近，滚动和输入期间不出现持续 Long Task。
7. 全量自动化测试通过后再部署；本轮不自动重启或替换运行容器。

## 10. 后续可选项

`app.js` 仍是约 717 KB 的无构建单文件。进一步拆分路由模块或引入稳定的压缩、代码分割流水线可以继续降低解析成本，但这属于构建体系改造，需要单独设计缓存、CSP、错误回退和部署原子性，不应在禁止构建且未建立资源清单的条件下直接机械拆分。
